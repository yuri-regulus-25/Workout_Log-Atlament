# Application Framework 設計引き継ぎ / TODO

## 0. この文書の目的

本書は、Application Framework（以下 AF）の基本設計で確定した事項と、今後の詳細設計で決定する事項を引き継ぐための作業文書である。

次回の設計作業では、本書を起点として AF の詳細設計を開始する。

重要事項:

- 本書で「決定済み」とした内容を、実装都合で独自変更しない。
- 未決事項は未決事項として扱い、推測で仕様を補完しない。
- 基本設計（BD）と詳細設計（DD）を混在させない。
- Frontend / 共通 JS / AF の責務境界を崩さない。

---

# 1. このシステムとは

筋力トレーニングログを閲覧・分析する個人用 Web Application。

同時に Frontend Framework 比較 PoC としての性格を持ち、MPA 構成で機能ドメインごとに異なる Frontend Framework を利用する。

現在の主要な画面構成:

```text
Portal / Entry
Dashboard                 React
Workout Domain             Vue 3
Workout Domain Details     Vue 3
Performance Detail         Angular
Analytics                  Svelte
```

Workout の正本データ（SoT）は GitHub 上の JSON / JSONL とする。

Master Data も GitHub 上で管理し、Workout Data は Master の ID を参照する。

Frontend Framework 自身には、データ取得・正規化等の共通処理を持たせない。

今後、Frontend が Runtime Data を利用するための Application Runtime として AF を導入する。

---

# 2. 全体アーキテクチャ上の AF の位置

基本的な責務境界は以下とする。

```text
Application Framework (AF)
          ↑↓ HTTP
       共通 JavaScript
          ↑↓ Call
 Frontend Framework / UI
```

原則:

- AF と共通 JS の境界は HTTP とする。
- 共通 JS と各 Frontend Framework の境界は共通 JS の Call Interface とする。
- Frontend Framework から AF の内部実装を意識させない。
- Frontend Framework から GitHub へ直接通信しない。
- OS 固有事情を共通 JS / Frontend Framework へ露出させない。

---

# 3. AF とは

AF は、本 Application を実行するための Application Runtime / Application Framework である。

AF は単なる Backend API ではない。

主として以下を担当する。

1. Runtime Data の管理・提供
2. GitHub 上の SoT と Local Runtime Data の同期・維持
3. GitHub Credential の管理
4. Build 済み Frontend Artifacts の管理・Hosting
5. Remote Data を利用できない場合の Local Runtime Data による継続手段の提供
6. localhost 上で Application Runtime を提供すること
7. AF 自身の状態・異常のうち、Frontend 側が認識する必要がある情報を提供可能とすること

AF は Frontend Framework の代わりに画面処理を行うものではない。

---

# 4. AF が管理するもの

基本設計時点で AF の管理対象とするもの:

- JSON
- JSONL
- Token
- Token Limit Date
- Frontend Artifacts（HTML / JS / CSS / その他 Build 成果物）

## 4.1 Runtime Data

GitHub 上の JSON / JSONL を SoT とする。

AF は Runtime で利用するための Local Data を管理する。

GitHub のディレクトリ構造を論理構造の基準とし、AF 実装ごとに独自の論理構造へ変更しない。

OS に起因する物理保存場所等の差異は AF 内部で吸収する。

## 4.2 Frontend Artifacts

AF は Build 済み Frontend Artifacts を保持し Hosting する。

AF は Frontend Build を実行しない。

したがって Runtime で以下を要求する構成は禁止する。

- npm build
- Node.js を利用した Frontend Build
- React / Vue / Angular / Svelte 等の CLI による Build
- Runtime Data 更新を理由とした Frontend Rebuild

Runtime Data と Frontend Build Artifacts は分離する。

---

# 5. AF の提供機能 — BD 決定済み

## 5.1 Runtime Data 提供

AF が管理する JSON / JSONL を、共通 JS から利用可能な形で提供する。

## 5.2 Runtime Data 同期

GitHub を SoT とし、Local Runtime Data を同期・維持する。

## 5.3 Frontend Hosting

Build 済み Frontend Artifacts を Hosting する。

Frontend Build は行わない。

## 5.4 Credential 管理

GitHub Token および Token Limit Date を AF が管理する。

Credential 自体を Frontend へ公開しない。

## 5.5 Runtime Data Fallback

Remote Data を利用できない場合でも、利用可能な Local Runtime Data が存在する場合は、それを利用する継続手段を AF が持つ。

注意:

これは GitHub / Remote → Local Runtime Data の Fallback であり、AF API Call の Fail 時に Frontend がどう動作するかとは別責務である。

## 5.6 Application Runtime

localhost 上で Frontend および Runtime Data の利用環境を提供する。

## 5.7 AF 状態・異常情報

ユーザーまたは Frontend が認識する必要がある AF 側状態を、共通 JS へ提供可能とする。

具体的な状態定義・Response・通知方式は DD で決定する。

---

# 6. AF 実装間の互換性原則 — BD 決定済み

原則は以下の一文に集約する。

> AF は、OS に起因する差異を除き、各実装間で仕様を共通化する。OS 固有の差異は各 AF 内部で吸収し、外部仕様へ影響させない。

想定実装には少なくとも Windows / WinForms 系および Android 系がある。

言語、Filesystem API、HTTP Server 実装、Process 管理、Secure Storage 等の OS / Platform 固有実装は各 AF 内部で吸収する。

ただし、それを理由として共通 JS / Frontend から見える仕様を変更しない。

---

# 7. Security 基本原則 — BD 決定済み

以下を AF の基本原則とする。

- Token その他 Credential を Frontend へ公開しない。
- GitHub 操作は Read Only とする。
- AF の HTTP 公開範囲は localhost に限定する。
- AF 管理外の Local Resource を Frontend から直接操作させない。
- Frontend から GitHub へ直接通信させない。

ログ・内部 Error への Credential 出力については BD では制約しない。

本システムは外部公開を前提としない個人利用 Application であり、ログ方針等の詳細は必要に応じて DD で決定する。

---

# 8. Lifecycle 責務 — BD 決定済み

AF は AF 自身の Lifecycle のみを管理する。

対象:

- AF 自身の起動
- AF 自身の稼働
- AF 自身の終了
- AF 自身が管理する Runtime / Resource の Lifecycle

AF は Frontend Framework や共通 JS の Lifecycle を管理しない。

## 8.1 共通 JS との境界

AF API の以下の判定は共通 JS の責務とする。

- Response が返ってきたか
- HTTP 通信として成立したか
- Response が期待する形式であるか
- API Call が Timeout したか

ここでいう「形式チェック」は Response の契約・構造に関する確認であり、Workout Data 等の業務内容そのものの正当性判断を意味しない。

## 8.2 AF 終了要求

共通 JS は、AF が利用継続不能と判断された場合に AF へ終了を要求できる。

ただし、共通 JS が OS Process を直接強制 Kill する責務は持たない。

概念上:

```text
共通 JS
  ↓ AF 終了要求
AF
  ↓ AF 自身の Lifecycle 制御
AF 終了
```

つまり、共通 JS は「終了してほしい」と要求できるが、外部から AF Process を強制終了する主体にはならない。

AF が終了要求そのものに応答できない場合、それ以上の Process 制御を共通 JS の責務とはしない。

具体的な終了要求 API、Timeout、AF 側終了処理は DD で決定する。

---

# 9. Fallback の責務境界 — BD 決定済み

「Fallback」という言葉が複数 Layer に存在するため、混同しないこと。

## AF 責務

```text
GitHub / Remote Data
        ↓ failure
Local Runtime Data
```

Remote を利用できない場合に Local Runtime Data を使用する判断・仕組みは AF の責務。

## 共通 JS 責務

```text
共通 JS
   ↓ AF API Call
AF
   ↓ timeout / invalid response / communication failure
共通 JS 側で Fail 処理
```

AF API Call の Fail をどう扱うかは共通 JS の責務。

Frontend Framework にこの共通 Fail 制御を持たせない。

---

# 10. AF の非責務 — BD 決定済み

AF は以下を責務としない。

## 10.1 Frontend Build

AF は Frontend Build を行わない。

Build 済み資材の Hosting のみを行う。

## 10.2 Frontend の実装・描画

以下は Frontend / Framework 側の責務。

- UI 描画
- DOM 操作
- Routing
- Framework 固有処理
- 画面状態管理

## 10.3 共通 JS の通信結果判定

以下は共通 JS の責務。

- AF API Response の形式チェック
- API Timeout 判定
- API Call Fail 時の Frontend 側制御
- Frontend 上でのユーザー通知
- AF への終了要求判断

## 10.4 業務データ内容の妥当性判断

AF は Data の管理・提供を行う。

Workout の値・内容等について「業務的に正しいか」を判断することは AF の責務ではない。

Data Syntax / Interface Contract 等、AF 自身の処理成立に必要な技術的検証をどこまで行うかは DD で決定する。

## 10.5 GitHub 更新

AF から GitHub への Write は行わない。

Commit / Push / Delete 等を AF の機能として持たせない。

# 11. 現時点の基本設計まとめ

```text
GitHub
  │
  │ Read Only
  │ JSON / JSONL / Master / etc.
  ▼
Application Framework
  ├─ GitHub = SoT
  ├─ Local Runtime Data 管理
  ├─ Token / Token Limit Date 管理
  ├─ Build 済み Frontend Artifacts 管理
  ├─ Frontend Hosting
  ├─ Remote → Local Fallback
  ├─ localhost HTTP
  └─ AF 自身の Lifecycle 管理
          │
          │ HTTP
          ▼
      共通 JavaScript
      ├─ API Call
      ├─ Response 形式確認
      ├─ Timeout 判定
      ├─ API Fail 制御
      ├─ User Notification
      └─ 必要時 AF 終了要求
          │
          │ Call
          ▼
Frontend Frameworks
  ├─ React
  ├─ Vue
  ├─ Angular
  └─ Svelte
```

外部から見た AF 仕様は OS によらず共通とする。

OS 差異は AF 内部で吸収する。

## DD-10. 禁止事項の具体化

少なくとも以下は実装仕様上も明示する。

- GitHub Write を行わない。
- Frontend Framework に AF / 共通 JS の責務を移さない。
- 共通 JS に OS 固有 Process 制御を持たせない。
- OS 固有事情を HTTP Interface に露出させない。
- 設計書に存在しない Cache / Fallback / Convenience Feature を実装者判断で追加しない。

# 14. 次回作業のゴール

最終的な目標は、Windows / WinForms 版 AF の実装担当へ設計一式を渡した際に、実装担当が独自の設計判断を挟まず実装開始できる状態にすることである。

特に LLM / Coding Agent に実装を依頼する場合、以下を満たすことを目標とする。

- 実装担当が不足仕様を推測する必要がない。
- 実装担当が「便利そうだから」という理由で仕様を追加する余地を最小化する。
- Runtime Data / Build / Cache / Fallback の責務を誤解しない。
- Windows 固有実装を外部 Interface に漏らさない。
- Frontend / 共通 JS / AF の責務境界を変更しない。
