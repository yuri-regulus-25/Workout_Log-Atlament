# v2.1.0 ユーザーテスト状況・指摘事項

> v2.1.0 Data Recovery のユーザーテストについて、2026-09-02 時点で確認できている結果、Correctness上の不具合、UI/UX上の指摘、未解決事項、再試験予定を退避するための資料。
> 単純なPASS/FAIL表ではなく、後から「なぜその判定になったか」まで復元できることを目的とする。

## 1. 現在のUT方針

### 目的
Windows / Android の双方で、Recoveryを次の一連の流れとして実際に操作し、正常に完走できることを確認する。

`Broken Resource → Draft → 自動保存 → Validation → Commit → Git反映 → 再検査 → Runtime反映`

CorrectnessとUI/UXは分けて判定する。

- 見た目や文言に違和感があっても、機能として正しければ指摘事項として記録しUTは継続する。
- 新しいCorrectness上のNGを発見した場合は、その地点でUTを停止して証跡を確保し、原因調査へ移る。

### 停止条件

> UT中に新しいCorrectness NGが出たら、その地点でUT停止 → 証跡確保 → 原因調査へ。UI上の違和感だけなら記録してUT継続。

この停止条件は、AndroidのUT-08で発動した。

### 試験内容

対象:

`data/workouts/2026/08/2026-08-22.json`

想定する操作・結果:

2. 対象を開く。
3. Draftを作成する。
4. 欠損値を入力する。
5. Draftが自動保存される。

### 初回試験で発生した問題

その後、主に次のCommitで修正が進められた。

- `08517db` — `fix: harden recovery commit reflection`
- `8e7d463` — `fix: serialize recovery draft autosave`
- `86c18a2` — `fix: complete recovery commit parity`

WindowsのRecovery取得処理は、raw branch refではなくGitHub Contents APIを利用する形へ変更された。

Androidでは同一PathへのRecovery Commitについて、GitHub Contents APIを使用し、source revision / draft revisionの競合確認とCommit後の反映処理まで実装された。

### UT-01 指摘 — Serializer / Git差分品質

Recovery自体は完走したが、生成されたGit差分に品質・Platform間差異の問題が見つかった。

Windows:

- おおむね `+58/-57` の全体書き換え。
- Property順序が変更された。
- 日本語等がUnicode escapeされた。

Android:

- おおむね `+1/-57`。
- 内容は正しいがJSON全体が1行へminifyされた。
- 日本語自体は可読状態で保持された。

判定:

- Windows データ内容: PASS
- Android データ内容: PASS
- Runtime利用可否: PASS
- Windows Serializer出力品質: 要改善
- Windows / Android Serializer整合性: 要改善

minifyそのものを禁止する、という意味ではない。

問題の中心は、Recovery設計上「通常Domain Model + canonical serializer」を使用する方針であるにもかかわらず、WindowsとAndroidで出力形式が大きく異なり、Git履歴に不要な差分を発生させている点にある。

対処する場合は、元JSONへの場当たり的な文字列Patchを作るのではなく、Platform間で共通のcanonical serialization contractを定め、それに従わせる方向を優先する。

## 7. UT-08 — Path Relocation

### 試験内容
Android試験用ブランチで、元々 `2026-08-07` を想定する日付欠損Resourceに対し、Recoveryで次の日付を入力した。

`2026/09/01`

この場合、canonical pathは次のように変更される。

変更前:

`data/workouts/2026/08/2026-08-07.json`

変更後:

`data/workouts/2026/09/2026-09-01.json`

### Commit前まで

**PASS**

確認事項:

- Validation成功。
- `修復できます` と表示された。
- Path変更が検出された。
- 変更前Path / 変更後Pathの警告が表示された。
- Commitが有効になった。
- 最終確認ダイアログにもPath変更が表示された。

ここまでの結果から、修復候補生成・Validation側ではPath Relocationが必要であることを認識できている。

### Commit実行

**FAIL — Correctness / v2.1.0 Freeze blocker**

`修復を確定` を実行するとHTTP 503となった。

Response:

```json
{
  "success": false,
  "errors": [
    {
      "code": "RECOVERY_WRITE_FAILED",
      "message": "Android Recovery relocation commit is unavailable in this build.",
      "recoverable": true
    }
  ],
  "warnings": [],
  "data": null
}
```

Gitには変更が発生しなかった。

これは「未実装状態で危険な部分書き込みをしなかった」という安全面では正しいが、Androidで必要なRecovery操作そのものが実装されていないため、UTとしてはFAIL。

### 原因
Androidは同一PathへのRecovery書き込みにはGitHub Contents APIを使用できるが、Path Relocationでは次の2操作が必要になる。

- 旧Pathを削除する。
- 新PathへResourceを作成する。

Recovery設計では、この2操作を別々のContents API Commitとして実行してはならない。

途中状態がGit履歴へ残り、Brokenな中間状態を作る可能性があるためである。

したがってPath Relocationは、**旧Path削除 + 新Path作成を1つのatomic Git Commitとして実行する必要がある。**

### 必要な修正方向

- Path RelocationではGit Data API相当の処理を使用する。
- 旧Path削除 + 新Path作成を1 Commitで行う。
- 保存先Pathを事前検証する。
- 既存Resourceへの暗黙上書きを禁止する。
- Source RevisionをCommit直前にも再確認する。
- Remote parent / headも再確認する。
- Optimistic concurrencyを維持する。
- 自動Rebaseしない。
- Force updateしない。
- Non-fast-forward updateしない。
- Commit直前の再Validationを必須とする。
- Git書き込み結果が不明瞭な場合、再試行前にRemote状態を照合する。
- Commit Messageは `Recover workout resource` を維持する。
- Commit後にSync・再検査・Runtime再構築を実行する。
- Git Commit成功後の反映失敗ではGitをRollbackしない。
- 正常反映後はDraftを削除する。
- 関係のないResourceを変更しない。
- 既存のAndroid同一Path Recoveryを壊さない。

最低限必要なRegression Test:

- Path Relocationのatomic commit成功。
- 保存先Resourceが既に存在する場合の衝突検出。
- Source / Remote head競合。
- Commit後のRuntime反映。

### 二次的なUI不具合 — Commit失敗がユーザーへ見えない
HTTP 503自体はAPIから返っていたが、Recovery UIでは意味のあるエラー表示が確認できなかった。

ユーザーから見ると、Commit Buttonが再び押せる状態へ戻っただけに近く、「何が失敗したのか」が分からない。

これはAndroid Path Relocation未実装とは別のUI/UX不具合として扱う。

必要な方向:

- Recovery APIのエラーを人間が理解できる形で表示する。
- 再試行可能なのか、別対応が必要なのかを判断できるようにする。
- Git書き込み結果が不明瞭な可能性があるケースでは、無条件の再Commitを唯一の導線にしない。

### UT-08総合判定

- Path変更検出: PASS
- Validation: PASS
- 最終確認: PASS
- Commit実行: FAIL
- Gitに不完全な変更を残さない安全性: PASS
- エラー表示: FAIL（UI/UX）
- 総合: **FAIL / Freeze blocker**

ここでCorrectness停止条件が発動した。

## 10. UT中に確認したRecovery共通UI/UX指摘

ここではRecovery操作中に見つかった指摘を退避する。

全画面を対象にしたUI/UXレビューについては別途作成する資料を正とする。

### 問題表示が人間向けになっていない
現在のRecovery画面では、次のような曖昧または実装寄りの表現が表示されることがある。

- `問題`
- `このデータを確認できません`
- `Workout required fields are invalid.`
- `対象: このデータ`
- `RUNTIME_DATA_INVALID`

指摘:

- 「何を確認できないのか」が分からない。
- `対象: このデータ` は情報としてほぼ意味がない。
- 英語の内部向けMessageを主要説明として出すべきではない。
- Error Codeは診断用の副次情報として扱うべき。

**具体的な日本語説明を主表示、CodeやLocation等の技術情報を副表示**とする方向が望ましい。

### Recovery一覧のBadge / Chip
一覧にはPath、問題件数、`ワークアウト`、`下書きあり` 等が表示される。

Light / Darkの双方で一部Chip・件数Badgeの視認性が弱い。

また、v2.1.0でRecovery対象として実際にWorkoutしか一覧へ出ないのであれば、`ワークアウト` Chipに情報価値があるか再検討余地がある。

ただし、実際の対応Resource範囲を確認せずに削除してはならない。

### Field Editorの情報密度
表示内容に対して縦方向の余白が大きく、画面占有量が多い。

Fieldと状態の対応関係を壊さない範囲で、よりcompactな表示を検討する。

Dark ModeではDate入力のCalendar Iconが見えにくい。

### Field状態の意味が視覚的に区別しにくい

`変更しました` と `復元できました` の見た目が、特にLight Modeでほぼ同じに見える。

意味は異なる。

- `変更しました`: ユーザーが値を変更した。
- `復元できました`: 元データから安全に値を復元できた。

色だけに依存せず、文言とSemantic Colorの両方で区別する必要がある。

具体的なColor Token割当はUI設計時に決める。

### Validation表示

- `修復内容を確認`
- `修復を確定`

これらの主要Actionは、独自の青色ではなく共通Themeの `primary` を利用する。

Dark ModeではValidation Alertの明度が低く、視認性が弱い。

Alertはcompact化し、他画面を含む共通方針として余白も統一する。UIレビューでは `mb-4` が候補として挙がっている。

Validation後にDraftを変更すると `内容が変更されたため、もう一度確認してください。` と再Validationを要求する挙動は確認できている。

### 元データ表示
設計上、元データ表示はread-onlyの診断・参照用機能であり、JSON Editorではない。

一方で、通常ユーザーにとってこの機能が本当に必要かは改めて検討対象。

- 診断時の補助情報として残す。
- 通常操作では不要として縮小・削除する。

どちらもあり得るため、自動的に削除する対象ではない。

残す場合、Dark Modeで大きな白背景が表示される現在の見た目はTheme対応が必要。

### 最終確認ダイアログ
`修復を確定` の前に最低限次を理解できる必要がある。

- 対象Resource / Path
- 保存先Path
- Validation結果
- Path変更の有無
- 変更したFieldと内容

Path表記は統一する。片側だけ `data/` を省略しない。

### Loading / Overlay
Loading / Progressの色は共通Theme `primary` を使用し、Dark Modeでも認識できるようにする。

ModalまたはLoading Overlay表示中は、背景のScrollおよび操作を禁止する。

## 11. UT-08以外のCorrectness・品質上の懸念

### Serializer整合性とGit差分汚染
UT-01ではWindows / Androidとも意味的に正しいResourceを生成できたが、Serializer出力は大きく異なった。

これは次の観点で問題候補となる。

- Git履歴が不要な差分で汚れる。
- Platformによって同じRecovery結果の表現が変わる。
- canonical serializerという設計意図と実装が一致していない可能性がある。

UT-08のatomic relocation未実装と同じ重大度とは限らないが、v2.1.0を製造品質として完了させる前に評価する。

### 試験用ブランチ変更とLocal Draft
AndroidのDraftは端末Localに保存されるため、Gitブランチを変更しただけでは消えない場合がある。

これは設計上不自然ではないが、手動UTでは混乱要因になる。

完全に初期状態から試験したいScenarioでは、ブランチ変更だけで初期化されたとみなさず、必要に応じてLocal Draftを明示的に削除・初期化する。

### API Errorと画面表示の整合性
UT-08ではAPIが503と具体的なErrorを返していても、画面からは失敗理由を理解できなかった。

したがってRecoveryの失敗系UTでは、API Responseだけでなく**ユーザーに何が表示されたか**も確認対象に含める。

## 12. Android 再試験予定

Token / 作業余力が回復した後、UT-08だけを直して再試験するのではなく、**すでにPASS判定だったAndroidのUTも再度実行する。**

目的は、後続修正を入れた状態と以前のPASS時点での挙動を比較し、既存動作を壊していないことを確認するため。

最低限、Androidで次を再確認する。

- Broken一覧表示
- Draft作成
- Draft自動保存
- ValidationによるCommit可否制御
- 同一PathへのCommit
- Commit後の反映
- 正常反映後のDraft削除
- Runtime上のデータ内容一致
- Corrupted Draftの影響分離
- 不正な修復候補のCommit禁止
- UT-08修正後のPath Relocation

これは過去のPASS判定を取り消すためではなく、**修正前後の動作比較を目的とした再試験**である。
