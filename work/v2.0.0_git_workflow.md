# v2.0.0 Git Workflow / Manufacturing Operation Rules

## 1. 目的

本書は、v2.0.0 製造における Git / Branch / GitHub Issue / Pull Request
の運用ルールを定義する。

目的は以下のとおり。

-   Planning → Architecture → Manufacturing の履歴を追跡可能に保つ。
-   GitHub Issue を実装作業単位、および中断時の再開地点として利用する。
-   SubPhase 単位の作業を Phase Branch へ統合し、Phase 単位で
    `release-2.0.0` へ統合する。
-   Phase ごとの統合境界を Git 履歴上で維持する。
-   意図しない Branch 作成、Merge、Rebase、Force Push を防止する。
-   Git 操作後に Local / Remote を意図的な乖離状態のまま放置しない。

本書を v2.0.0 製造時の Git 運用上の Source of Truth とする。

------------------------------------------------------------------------

## 2. 製造開始時の Branch 構造

v2.0.0 の設計系統は以下とする。

``` text
develop
└─ release-2.0.0-planning
   └─ release-2.0.0-architect
      └─ release-2.0.0
```

### Branch の責務

#### `develop`

v2.0.0 Planning 開始時の基底 Branch。

#### `release-2.0.0-planning`

v2.0.0 の調査・企画・Planning 履歴を保持する。

製造用 Branch として使用しない。

#### `release-2.0.0-architect`

v2.0.0 の仕様設計 Fix 履歴を保持する。

Phase 0 ～ Phase 11 の製造仕様・作業指示は、この系統で Fix
された内容を基準とする。

製造開始後の通常実装では変更しない。

#### `release-2.0.0`

v2.0.0 の製造統合 Branch。

`release-2.0.0-architect` の Fix 済み HEAD から作成する。

Phase 0 ～ Phase 11 の製造成果を順次統合する。

------------------------------------------------------------------------

## 3. 製造 Branch 階層

各 Phase の製造では以下の Branch 階層を使用する。

``` text
release-2.0.0
└─ feature-2.0.0-phaseX
   └─ feature-2.0.0-phaseX-X
```

-   `feature-2.0.0-phaseX`
    -   Phase X の統合 Branch。
-   `feature-2.0.0-phaseX-X`
    -   Phase X 内の個別作業 Branch。
    -   原則として対応する GitHub Issue 単位で作成する。

例:

``` text
release-2.0.0
└─ feature-2.0.0-phase0
   ├─ feature-2.0.0-phase0-a
   └─ feature-2.0.0-phase0-b
```

本書で定義した階層以外の Branch 構造を、Codex / Automation
が独自判断で追加・変更してはならない。

------------------------------------------------------------------------

## 4. Phase 開始

Phase X の開始時は以下を実施する。

1.  直前 Phase の成果が `release-2.0.0` に統合済みであることを確認する。
2.  Local / Remote の状態を同期・確認する。
3.  最新の `release-2.0.0` HEAD から `feature-2.0.0-phaseX` を作成する。
4.  `feature-2.0.0-phaseX` を Remote へ Push する。
5.  Local / Remote の Branch 状態を確認してから SubPhase
    作業を開始する。

``` text
develop
└─ release-2.0.0-planning
   └─ release-2.0.0-architect
      └─ release-2.0.0
         └─ feature-2.0.0-phaseX
```

------------------------------------------------------------------------

## 5. SubPhase / Issue 作業開始

Phase X-X の作業開始前に以下を実施する。

1.  対応する GitHub Issue を特定する。
2.  対応する v2.0.0 製造仕様・作業指示を確認する。
3.  同一 Phase 内の先行 SubPhase が `feature-2.0.0-phaseX`
    に統合済みであることを確認する。
4.  **最新の `feature-2.0.0-phaseX` HEAD から** `feature-2.0.0-phaseX-X`
    を作成する。
5.  作業 Branch を Remote へ Push する。

``` text
develop
└─ release-2.0.0-planning
   └─ release-2.0.0-architect
      └─ release-2.0.0
         └─ feature-2.0.0-phaseX
            └─ feature-2.0.0-phaseX-X
```

後続 SubPhase は、それ以前の SubPhase の統合結果を含む最新 Phase Branch
から作成する。

複数の SubPhase Branch を古い Phase HEAD から事前に一括作成しない。

------------------------------------------------------------------------

## 6. SubPhase 作業中

作業中は以下を遵守する。

-   対応 Issue と製造仕様の Scope 内で実装する。
-   `release-2.0.0-planning` を変更しない。
-   `release-2.0.0-architect` を通常の製造作業から変更しない。
-   `release-2.0.0` へ直接実装しない。
-   `feature-2.0.0-phaseX` へ直接実装しない。
-   実装 Commit は `feature-2.0.0-phaseX-X` に作成する。
-   適切な作業区切りで Remote へ Push し、再開可能な状態を維持する。

### 中断・再開

GitHub Issue を作業の Canonical Restart Anchor とする。

作業を中断した場合、Issue / Branch / PR
から少なくとも以下を追跡可能にする。

-   何を実装していたか。
-   どの仕様が適用されるか。
-   どこまで完了しているか。
-   何が残っているか。
-   どの Branch に作業状態が存在するか。

再開時は対応 Issue を起点として作業状態を確認する。

------------------------------------------------------------------------

## 7. SubPhase 完了

Phase X-X の実装完了時は以下を実施する。

1.  対応仕様で要求される Test / Check を実行する。
2.  Issue の完了条件を満たしていることを確認する。
3.  最終 Commit を Remote へ Push する。
4.  以下の Pull Request を作成する。

``` text
feature-2.0.0-phaseX ← feature-2.0.0-phaseX-X
```

GitHub 上では:

``` text
Base: feature-2.0.0-phaseX
Head: feature-2.0.0-phaseX-X
```

5.  PR 本文に対応する GitHub Issue を明記する。
6.  Review および必要な Check を実施する。
7.  Repository で承認された Merge 方法により PR を Merge する。
8.  Remote の `feature-2.0.0-phaseX` に Merge
    結果が存在することを確認する。
9.  Merge 確認後、対応する Phase X-X Issue を Close する。
10. 不要になった SubPhase Branch を削除する。

### Issue Close

SubPhase PR の Base は Default Branch ではないため、GitHub の Closing
Keyword による自動 Close のみに依存しない。

**Phase X-X Issue は、PR が `feature-2.0.0-phaseX` へ正常に Merge
され、その結果を確認した時点で完了とし、明示的に Close する。**

------------------------------------------------------------------------

## 8. 次 SubPhase 開始

Phase X-X 完了後:

``` text
develop
└─ release-2.0.0-planning
   └─ release-2.0.0-architect
      └─ release-2.0.0
         └─ feature-2.0.0-phaseX
```

次の Phase X-Y は、X-X の成果を含む最新 Phase Branch から作成する。

``` text
develop
└─ release-2.0.0-planning
   └─ release-2.0.0-architect
      └─ release-2.0.0
         └─ feature-2.0.0-phaseX
            └─ feature-2.0.0-phaseX-Y
```

以後、

``` text
Issue
→ Branch
→ Implementation
→ Test
→ PR
→ Merge
→ Issue Close
```

を繰り返す。

------------------------------------------------------------------------

## 9. Phase 完了

Phase X は以下をすべて満たした時点で完了とする。

-   Phase 内の予定 SubPhase がすべて完了している。
-   SubPhase 関連 Issue がすべて Close されている。
-   SubPhase PR がすべて `feature-2.0.0-phaseX` に統合されている。
-   Phase 単位の Integration Test / 完了条件を満たしている。
-   Child Branch のみに残っている必要な成果が存在しない。

完了後、以下の PR を作成する。

``` text
release-2.0.0 ← feature-2.0.0-phaseX
```

GitHub 上では:

``` text
Base: release-2.0.0
Head: feature-2.0.0-phaseX
```

Review / Check 完了後:

1.  Phase PR を Merge する。
2.  Phase の統合境界を Git 履歴上で維持する。
3.  Merge 方法として選択可能な場合、原則として Non-Fast-Forward
    の統合履歴を残す。
4.  Remote の `release-2.0.0` に Phase 成果が存在することを確認する。
5.  Phase 全体を追跡する Issue が別途存在する場合は、Phase 統合確認後に
    Close する。
6.  不要になった Phase Branch を削除する。

その後、次 Phase は最新 `release-2.0.0` から開始する。

------------------------------------------------------------------------

## 10. Phase 0 ～ Phase 11 製造期間

Phase 0 から Phase 11 まで、前述の運用を順番に繰り返す。

製造期間中は以下を禁止する。

-   通常の Phase 作業途中で `release-2.0.0` を `develop` へ Rebase
    する。
-   Codex / Automation が独自判断で `develop` の変更を Child Branch
    へ取り込む。
-   Planning / Architecture 履歴を書き換える。
-   Phase / SubPhase Branch の親子関係を独自判断で変更する。
-   Human Approval なしに Rebase / Force Push を実行する。

製造中の概念的な系統は以下を維持する。

``` text
develop
└─ release-2.0.0-planning
   └─ release-2.0.0-architect
      └─ release-2.0.0
         ├─ Phase 0 integration
         ├─ Phase 1 integration
         ├─ ...
         └─ Phase 11 integration
```

------------------------------------------------------------------------

## 11. Phase 0 ～ 11 全件完了後の Rebase

Phase 0 ～ Phase 11 の全製造作業が完了した後に限り、`release-2.0.0`
を最新 `develop` 上へ Rebase する。

### Rebase 前提条件

以下をすべて確認する。

-   Phase 0 ～ Phase 11 の成果が `release-2.0.0` に統合済み。
-   対応する製造 Issue が完了済み。
-   必要な未 Merge Child Branch が存在しない。
-   Working Tree が Clean。
-   Local / Remote の状態を確認済み。
-   最新の Remote 情報を Fetch 済み。

### Rebase

Phase 単位の Merge 履歴を維持するため、Git CLI
を使用する場合の基本形は以下とする。

``` bash
git rebase --rebase-merges develop
```

実行前に Current Branch / Upstream / Working Tree / Remote State
を必ず確認する。

Conflict が発生した場合、v2.0.0
の仕様・実装への影響を確認し、人間の判断を伴って解決する。

機械的に片側を採用してはならない。

### Rebase 後

1.  必要な Final Integration Test を実施する。
2.  Git Graph / Commit History を確認する。
3.  Rebase 後の `release-2.0.0` を安全に Remote へ反映する。
4.  Local / Remote の同期状態を再確認する。

Rebase は Commit SHA を変更するため、旧 `release-2.0.0`
履歴へ依存する作業 Branch が残っている状態では実施しない。

概念上の最終状態:

``` text
develop
├─ release-2.0.0-planning
│  └─ release-2.0.0-architect
└─ release-2.0.0
```

`release-2.0.0-planning` / `release-2.0.0-architect`
は設計履歴として維持し、`release-2.0.0` は最新 `develop` を基底とした
v2.0.0 製造成果となる。

------------------------------------------------------------------------

## 12. Local / Remote 同期

Git 操作は、意図した Local / Remote
状態が一致するまでを一連の作業として扱う。

Branch 作成、Merge、Rebase、Branch 削除等の後は:

1.  Current Branch を確認する。
2.  Local / Remote の Ahead / Behind を確認する。
3.  必要な Push / Fetch を行う。
4.  最終状態を再確認する。

Remote で削除済みの Remote-Tracking Branch は Prune する。

``` bash
git fetch --prune
```

必要に応じて以下を設定してよい。

``` bash
git config --global fetch.prune true
```

Remote で削除済みの Branch を、通常作業状態で誤解を招く `origin/...`
参照として意図的に残さない。

------------------------------------------------------------------------

## 13. Rebase / Force Push Safety

Rebase は履歴を書き換える。

Rebase 後に Remote Branch の更新が必要な場合は、原則として:

``` bash
git push --force-with-lease
```

を使用する。

通常の:

``` bash
git push --force
```

は Human Approval なしに使用しない。

Force Update 前に以下を確認する。

-   対象 Branch 名。
-   Remote の現在 HEAD。
-   書き換える履歴へ依存する Active Work が存在しないこと。
-   Working Tree が Clean であること。
-   Rebase 後の履歴が意図どおりであること。

製造上の Cleanup を理由として `master` / `develop` / Planning /
Architecture の履歴を付随的に Rewrite してはならない。

------------------------------------------------------------------------

## 14. Codex / Automation 運用

実装依頼が存在すること自体を、Git Topology
を自由に変更する許可と解釈してはならない。

Codex / Automation は、Human から明示的な別指示がない限り:

-   本書の Branch 階層に従う。
-   実装開始前に対応 Issue を特定する。
-   Issue を作業単位・再開地点として扱う。
-   対応 SubPhase Branch 上でのみ実装する。
-   SubPhase PR の Base を対応 Phase Branch とする。
-   Phase PR の Base を `release-2.0.0` とする。
-   PR に対応 Issue を明記する。
-   Test / Completion Criteria を確認してから統合を要求する。
-   許可された Git 操作後は Remote まで同期する。
-   無関係な Release / Planning / Architecture Branch を作成しない。
-   Human Approval なしに Rebase / Force Push しない。
-   通常実装の都合で Fix 済み Architecture 仕様を変更しない。

現在の Git
状態が本書の想定と一致しない場合、**勝手に修復せず作業を停止し、差異を報告する。**

------------------------------------------------------------------------

## 15. Issue / Branch / PR Traceability

各実装作業は以下の関係を追跡可能にする。

``` text
GitHub Issue
    ↓
feature-2.0.0-phaseX-X
    ↓
PR to feature-2.0.0-phaseX
    ↓
Phase Integration
    ↓
PR to release-2.0.0
```

GitHub Issue は:

1.  実装作業の定義・追跡単位。
2.  作業中断時の再開地点。

の両方として使用する。

PR には関連 Issue を明記する。

1つの PR が正当に複数 Issue を対象とする場合は、対象 Issue
をすべて明示する。

無関係な Issue の作業を説明なしに同一 PR へ混在させない。

------------------------------------------------------------------------

## 16. Human Review Boundary

本書の Workflow は、自動的な Merge 権限を付与するものではない。

以下は Human Review / Approval の対象とする。

-   実装受入。
-   PR Merge。
-   Conflict Resolution。
-   Phase 完了判定。
-   Final Rebase 実行。
-   Force Update。
-   本 Workflow からの逸脱。

意図的に Workflow を逸脱する場合、後から理由を追跡できるよう、関連 Issue
/ PR 等へ理由を残す。

------------------------------------------------------------------------

## 17. 全体フロー

``` text
# Design Lineage

develop
└─ release-2.0.0-planning
   └─ release-2.0.0-architect
      └─ release-2.0.0


# Phase X

release-2.0.0
└─ feature-2.0.0-phaseX
   └─ feature-2.0.0-phaseX-X
        │
        └─ GitHub Issue


# SubPhase Complete

feature-2.0.0-phaseX
    ↑ PR / Merge
feature-2.0.0-phaseX-X

→ Merge 確認
→ Issue Close
→ 最新 Phase HEAD から次 SubPhase を作成


# Phase Complete

release-2.0.0
    ↑ PR / Merge
feature-2.0.0-phaseX

→ Phase Integration 確認
→ 最新 release HEAD から次 Phase を開始


# Phase 0 ～ 11 Complete

latest develop
    ↑ rebase --rebase-merges
release-2.0.0

→ Final Integration Test
→ History Review
→ Safe Remote Synchronization
```

------------------------------------------------------------------------

## 18. Core Principle

**Planning が意図を定義し、Architecture が仕様を Fix する。Issue
が実装単位を定義し、SubPhase Branch が実装する。Phase Branch が Phase
内を統合し、`release-2.0.0` が Release 全体を組み立てる。Phase 0 ～ 11
完了後、Final Rebase により完成した v2.0.0 を最新 `develop`
上へ載せ直す。**
