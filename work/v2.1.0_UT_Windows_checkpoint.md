調査日: 2026-09-06
最終調整日: 2026-09-07

## 目的

UT-01で確認された Recovery 実行後の日本語文字列が `\uXXXX` 形式になる事象について、修正前の原因切り分けを記録する。

本ファイルは修正仕様ではなく、Windows UT-01 の調査チェックポイントである。現在のSTOP要因や手動UTの進行状況は `work/v2.1.0-UT.md` を正とする。

## 2026-09-07時点の位置づけ

このファイルで扱う日本語escape問題は、UT-01の機能完走を止めたCorrectness STOP要因ではない。

既に別修正で解消済みのCorrectness要因:

- Windows: Commit成功後もBroken inventoryが残る問題は、branch raw readではなくGitHub Contents API/committed revisionを使う修正で対応済み。
- Android: same-path Recovery commitが503になる問題は、Android commit実装追加で対応済み。
- Android: UT-08 Path Relocationが503になるSTOP要因は、GraphQL `createCommitOnBranch` による atomic relocation commit 実装で対応済み。

本ファイルに残す論点:

- Windows RecoveryがRepositoryへ保存するJSONで、日本語が `\uXXXX` escapeされる出力品質問題。
- Windows / Android のRecovery serializer出力が一致せず、Git差分が不要に大きくなる品質問題。

この論点はCorrectness NGではなく、製造品質・canonical serialization contractの確認対象として扱う。

## 結論 / 現時点の最有力箇所

GitHubへの送信処理そのものより、Recovery の置換候補データを生成する `BuildCandidateContent(RecoveryDraft draft)` が最有力。

特に以下の `JsonObject.ToJsonString(AfJson.Options)` により、Repositoryへ保存するJSON文字列を生成した時点で、日本語が System.Text.Json の既定エンコードにより `\uXXXX` 形式へエスケープされている可能性が高い。

```csharp
private static string BuildCandidateContent(RecoveryDraft draft)
{
    ...

    // JSONL系
    .Select(obj => obj.ToJsonString(AfJson.Options));

    ...

    // 単一JSON系
    return BuildObjectFromFields(fields, "").ToJsonString(AfJson.Options) + Environment.NewLine;
}
```

次にserializer品質へ着手する場合は、まずここを起点に確認する。

## DevToolsで確認した境界

Recovery Draft のPOSTについて確認。

- Request body: 日本語は通常の日本語文字列として送信されている。
- Response の Raw JSON: 日本語部分は `\uXXXX` 表現になる。
- Response の Preview: JSONとしてparseされた値は正常な日本語として表示される。

したがって、Draft APIのRaw Responseに `\uXXXX` が存在すること自体は、JSON wire representationとして正常であり、この時点だけではデータ破損とは判断しない。

一方、Validate結果の `replacementContent` は「Repositoryへ保存するJSONそのものを格納した文字列」であり、その内部JSONに `\uXXXX` が含まれていることを確認した。

例:

```json
{
  "note": "4rep\u4ED8\u8FD1..."
}
```

この `replacementContent` は後段でGitHubへ書き込まれるため、Repository上の成果物が人間可読な日本語ではなく `\uXXXX` になる直接原因になり得る。

## Breakpointで確認した内容

GitHub書き込み側の `PushRecoverySamePathAsync(...)` で停止して確認したところ、引数 `replacementContent` は同メソッドへ到達した時点ですでに `\uXXXX` を含む状態だった。

したがって、少なくとも以下は「最初に変換した場所」ではない可能性が高い。

- GitHub Contents APIへのPUT
- `Encoding.UTF8.GetBytes(replacementContent)`
- Base64変換
- GitHub側での保存処理

GitHub送信処理は、すでに生成済みの `replacementContent` を転送しているだけと考えられる。

## AfJson.Options

確認した設定:

```csharp
public static readonly JsonSerializerOptions Options = new()
{
    PropertyNamingPolicy = JsonNamingPolicy.CamelCase,
    PropertyNameCaseInsensitive = true,
    WriteIndented = true
};
```

カスタム `Encoder` は設定されていない。

System.Text.Json の既定serializationでは非ASCII文字が `\uXXXX` 形式になるため、APIレスポンスとしては意味的に問題ないが、Repositoryへ保存する人間可読JSONのcanonical representationとして同じOptionsを利用することが適切かは要検討。

API wire用serializationとRepository永続化用serializationを同一設定で扱っている点も設計上の確認対象とする。

## 次回の最短確認手順

`BuildCandidateContent` にBreakpointを置き、同一のnote等について次を比較する。

1. `BuildObjectFromFields(...)` が返した `JsonObject` 内のleaf値を `GetValue<string>()` で確認する。
2. その値が通常の日本語であることを確認する。
3. 同じ `JsonObject` に対して `ToJsonString(AfJson.Options)` を実行した結果を確認する。
4. `ToJsonString` 後に初めて文字列中へ literal な `\\u` が現れるなら、変換地点を確定できる。

デバッガの `Json` 表示自体がserialization済み表現を表示する場合があるため、Locals上で `\uXXXX` に見えることだけでは判定しない。必ずleafの `GetValue<string>()` と、生成後stringを比較すること。

## Codexへの引き継ぎポイント

最初に調べる場所:

- `RecoveryService.BuildCandidateContent(RecoveryDraft draft)`
- `BuildObjectFromFields(...)`
- `JsonObject.ToJsonString(AfJson.Options)`
- `AfJson.Options`

確認事項:

- `BuildObjectFromFields` 時点のleaf文字列は日本語のままか。
- `ToJsonString(AfJson.Options)` がRepository用文字列を `\uXXXX` 化する境界になっているか。
- JSON単一ドキュメントとJSONL (`sessions`) の双方で同じ問題が発生するか。
- APIレスポンス用Optionsを変更するのではなく、Repository保存用serialization policyを分離すべきか。
- 修正後、Repositoryへ保存されるJSONが日本語を保持しつつ、有効なJSON/JSONLとしてparse可能か。
- 既存UTおよびRecoveryのcanonical format要件を壊さないか。

## 修正方針についての注意

現時点ではserializer品質問題の修正方法は確定していない。

候補としてRepository保存専用の `JsonSerializerOptions` / Encoderを用意する方法が考えられるが、`AfJson.Options` をグローバルに変更するとAPI wire representation等にも影響するため、影響範囲を確認してから決定すること。

`JavaScriptEncoder.UnsafeRelaxedJsonEscaping` 等を利用する場合も、Repositoryへ保存するJSONという用途、既存canonical format、文字・記号のescaping要件を確認したうえで採用判断すること。

## その他の調査メモ

Windows側のRecovery処理を追跡した際、大きな責務が `AfServices.cs` に集中しており、処理経路の把握に時間を要した。

これは今回のUT-01修正とは分離し、将来のリファクタリング対象とする。v3.0.0では責務単位でのファイル/モジュール分割、APIとRepository等の境界明確化、コメント方針を含む製造規約の策定を検討する。

今回のv2.1.0では構造リファクタリングを同時実施せず、Correctness STOP要因の修正と回帰確認を優先する。

## 現在地

**Correctness STOP要因ではなく、serializer品質・platform整合性の調査チェックポイント。**

現時点では次の仮説を保持する:

> Draftの値自体ではなく、`BuildCandidateContent` がRepositoryへ保存するJSON文字列を `ToJsonString(AfJson.Options)` で生成する際に、日本語を `\uXXXX` へescapeしている可能性が高い。対応する場合は、Repository保存用serialization policyの分離を含めて検討すること。
