# Atlament Next — Remaining Design Topics

現時点で基本方針が確定していない、または詳細化が必要な設計項目を整理する。
本資料に記載する項目は原則として未FIXとし、今後の設計時に検討する。

---

## 1. Initial Setup Guidance

Native Host Applicationの初回起動時、Local Data Storageが存在しない場合に実行するSetup Guidanceの仕様を決定する。

### 検討事項

- Setup Guidanceの開始条件
- GitHub Tokenの登録方法
- Private Repositoryの指定方法
- Branchの指定方法
- JSON取得元ディレクトリの指定方法
- 入力内容のValidation
- GitHub接続確認をどのタイミングで実施するか
- Token不正時の振る舞い
- Repository / Directoryが存在しない場合の振る舞い
- Setup途中でApplicationを終了した場合の扱い
- Setup完了条件
- Setup完了後の初回同期処理
- Setup情報の再設定方法

UI詳細については別途検討する。

## 2. Local Data Directory Structure

GitHubから取得したJSONデータをApplication管理領域へ保存する際のディレクトリ構造を決定する。

### 現時点の前提

- Git Repository自体のcloneは原則行わない
- Git関連Metadataは保持しない
- 必要なJSONディレクトリのみ取得する
- Source of TruthはPrivate GitHub Repositoryとする
- Local DataはFrontend表示およびOffline利用のためのLocal Copyとして扱う

### 検討事項

- Application Data Root
- Current Data Directory
- Backup Directory
- Temporary Download Directoryの必要性
- JSON取得時のDirectory単位での置換方法
- 不要ファイルが存在した場合の扱い
- Application終了時に一時データが残った場合のRecovery方法

---

## 3. Data Synchronization Sequence

Application wake up時および手動更新時の詳細な同期Sequenceを決定する。

### 確定済み前提

- Application wake up時に毎回GitHubからデータ取得を試行する
- 手動Refreshを許可する
- GitHub RepositoryへのWriteは禁止する
- 更新の有無に関係なく取得データでLocal Dataを置換する
- GitHub取得失敗時は既存Local Dataを利用する
- Frontendは同期処理完了後に取得結果APIを参照する
- 同期中はLoading状態とする

### 検討事項

- HTTP Request開始タイミング
- Frontend Hosting開始と同期開始の順序
- 同期完了判定
- 同期Status APIのResponse Schema
- 手動Refresh APIのEndpoint
- Refresh中に再度Refresh要求された場合の扱い
- Network Timeout
- Retryを実施するか
- Retryを実施する場合の回数・間隔
- Application wake up直後にNetworkが利用できない場合の扱い

---

## 4. Atomic Data Replacement / Rollback

GitHubから取得したデータによって既存正常データを破壊しないための詳細な更新方式を決定する。

### 現時点の基本Sequence

```text
Existing Local Data
        ↓
BackupへRename
        ↓
New Data取得
        ↓
Validation
    ┌───┴───┐
 Success   Failure
    ↓         ↓
Backup削除   New Data削除
              ↓
          BackupをRevert
```

### 検討事項

- Rename対象Directory
- Temporary Directoryを別途利用するか
- Validationの具体的な範囲
- JSON Parse成功のみを正常とするか
- 必須JSONの存在確認を行うか
- 必須PropertyのValidationを行うか
- Download途中でApplication Processが終了した場合のRecovery
- Backup Directoryが既に存在した場合のRecovery
- Current / Backup双方が存在する異常状態からのRecovery
- File System操作失敗時の扱い

## 5. Localhost HTTP API Contract

Native HostとFrontend間の唯一の共通境界となるHTTP API Contractを設計する。

### 確定済み前提

- Frontend CommunicationはHTTP Request / Responseを基底とする
- Native BridgeによるPlatform差異をFrontend側で吸収しない
- FrontendはHost Platformを認識しない
- Native HostがFrontend AssetsもHostingする
- Frontendは可能な限りRelative URLでAPIへアクセスする

### 検討事項

- API Base Path
- Data取得Endpoint
- Sync Status Endpoint
- Manual Refresh Endpoint
- Application Status Endpoint
- Token Expiration情報Endpoint
- Error / Warning情報Endpoint
- HTTP Status Code Policy
- Response JSON共通Format
- Error Response Schema
- API Versioningを設けるか
- Cache-Control等のHTTP Header Policy
- localhost以外からのRequestを拒否する方法

## 6. Localhost Server Lifecycle

Native Hostが管理するlocalhost HTTP Serverの詳細なLifecycleを決定する。

### 確定済み前提

- Primary Port: `14108`
- Secondary Port: `45194`
- Primaryが使用不可の場合はSecondaryを使用する
- 両方使用不可の場合はError表示後Applicationを終了する

### 検討事項

- Port使用可否の判定方法
- Server Bind Address
- `localhost` / `127.0.0.1` / loopback interfaceの扱い
- Host起動完了判定
- Server起動失敗時のCleanup
- Application終了時のServer Shutdown Sequence
- 想定外Exception発生時のServer Shutdown
- FrontendからHost Process終了を要求可能とするか

## 7. Single Instance Control

Applicationの多重起動を防止する実装方式を決定する。

### 確定済みBehavior

```text
Application Wake Up
        ↓
Existing Process?
   ┌────┴────┐
   NO       YES
   ↓          ↓
Start       Error
              ↓
             OK
              ↓
      New Process Kill
```

既存Application Processは終了させない。

### 検討事項

- Process Name判定
- Mutex等によるSingle Instance制御を利用するか
- Existing Process検出方法
- 異常終了後にLock情報が残る可能性への対応

## 8. Credential Management

GitHub TokenおよびToken Metadataの管理方式を決定する。

### 確定済み前提

- TokenはNative Host Application System側で管理する
- FrontendへTokenを公開しない
- Token登録日時 / 更新日時を保持する
- Token期限10日前からPortalへWarningを表示する
- Token更新時は期限判定用情報も更新する

### 検討事項

- Windows上で利用するSecure Storage
- Token登録日時 / 更新日時の保存場所
- Token Expiration Dateを直接保持するか
- 登録 / 更新日時から算出する場合の計算方式
- GitHub APIから取得可能な期限情報との関係
- Token更新処理
- Token削除処理
- Token失効時の判定方法
- Token権限不足時の扱い
- 必要最小限のGitHub Token Scope

## 11. Offline / Network Failure Behavior

NetworkまたはGitHub APIが利用できない場合の詳細Behaviorを決定する。

### 基本方針

Local Dataが存在する場合:

```text
Sync Failure
    ↓
Alert Information
    ↓
Existing Local Data
    ↓
Frontend利用継続
```

Local Dataが存在しない場合:

```text
Sync Failure
    ↓
Frontend表示用Dataなし
    ↓
Setup / Error State
```

### 検討事項

- Network ErrorとGitHub API Errorを区別するか
- Alert情報をどこまでFrontendへ渡すか
- 最終正常同期日時を表示するか
- Manual RetryのBehavior
- Offline状態の判定方法

---

## 12. Host Exception Policy

Native Host内部でExceptionが発生した場合の基本的な処理方針を整理する。

### 基本原則

- 既存正常Local Dataを破壊しない
- 不完全な取得データを正常データとして採用しない
- CredentialをError Response等へ含めない
- Recover可能なExceptionではLocal Dataを利用してFrontendを継続可能とする
- Recover不能なSystem ErrorではApplicationを安全に終了する

### 検討事項

- Recoverable / Fatal Exceptionの分類
- Fatal Error時のCleanup Sequence
- localhost Server終了保証
- Temporary Data削除保証
- Backup Revert失敗時の扱い

---

## 13. Local Data Delete / Reset

Application SystemからLocal Dataを削除する場合の詳細Behaviorを決定する。

### 確定済み前提

```text
Delete Local Data
       ↓
Local Data削除
       ↓
localhost Shutdown
       ↓
Application Process Kill
```

次回起動時:

```text
Local Dataなし
      ↓
Setup Guidance
```

### 検討事項

- Local Dataのみ削除するか
- Application Settingsも同時削除可能とするか
- Token削除を別操作とするか
- Full Reset機能を設けるか
- Backup / Temporary Dataも削除対象とするか
- 削除失敗時にProcessをKillするか否か

## 15. Security Boundary

個人利用Applicationではあるが、Native HostとFrontend間の最低限のSecurity Boundaryを決定する。

### 基本原則

- GitHub TokenをFrontendへ公開しない
- TokenをHTTP Responseへ含めない
- TokenをFrontend JavaScriptへ埋め込まない
- GitHubへのWrite権限を持たせない
- localhost APIを外部Networkへ公開しない
- CredentialをDebug Logへ出力しない

### 検討事項

- loopback interfaceのみBindすることを必須とするか
- Host Header等のValidation
- localhost APIに独自Authenticationが必要か
- Browser等の別OriginからのRequestをどう扱うか
- CORS Policy
- CSRF相当のLocalhost攻撃をどこまで考慮するか
