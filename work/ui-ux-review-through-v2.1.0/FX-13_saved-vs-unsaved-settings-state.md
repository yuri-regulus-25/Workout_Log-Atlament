# FX-13 保存済み設定と未保存フォーム状態を混同しない

## 概要

Application Settingsで、保存済み設定の状態と、画面上で編集中の未保存値を同じ「登録済み」状態として見せない。

これは見た目だけではなく、ユーザーへ伝える状態のCorrectnessに関わる。

## 確認した現象

確認画像: `Codex 画像 2026年9月2日 01_10_31.png`

Repository Sourceの `Branch` を画面上で `a` に変更しているが、保存前の状態でもInitial Setup側には次の表示が残っている。

```text
リポジトリ情報
リポジトリ情報は登録されています
```

この表示だけを見ると、画面上に見えている `a` が既に登録済みであるように解釈できる。

## 注意

036.mdのAssistant Responseでは「保存済み設定が存在するかだけを見ているのではないか」という実装原因が推測されている。

**実装原因は確認されていないため、この資料では事実として扱わない。**

Repository調査時に実際の状態判定を確認すること。

## 要求

少なくともユーザーが次を区別できること。

- 保存済み設定が存在し、フォームも保存済み内容と一致している状態。
- 保存済み設定は存在するが、フォームに未保存の変更がある状態。
- 設定自体が未登録の状態。

未保存値を編集している最中に、現在フォームへ表示されている内容まで「登録されています」と誤認させない。

## 会話中に提示された状態表現候補

```text
保存済み・変更なし
→ 登録されています

未保存の変更あり
→ 変更が保存されていません

未設定
→ 設定が必要です
```

文言そのものは候補であり、031〜045の範囲では最終文言として確定していない。

## Repository Source側の表示候補

036.mdではSave付近へ「未保存の変更」等を表示する案も提示されている。

これも改善候補として保持するが、配置・文言は確定していない。

## 受入条件

1. Form値を変更しただけでは、その変更内容を保存済みであるかのように表示しない。
2. Save成功後は未保存状態が解除され、保存済み状態へ戻る。
3. 未設定状態と、設定済みだが編集中の状態を区別できる。
4. 保存に失敗した場合、保存済み状態へ遷移しない。
5. 状態判定の実装は実際のpersisted stateとform stateを根拠にする。

## 重要度

余白・配置等の純粋なVisual改善より重要度が高い。UIが事実と異なる状態を示す可能性があるため、Correctness寄りのUX指摘として扱う。
