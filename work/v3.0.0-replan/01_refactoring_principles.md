# リファクタリング共通原則

## 1. 目的

Atlament全体を、人間が責務と変更影響を局所的に理解できる構造へ移行する。

「巨大なファイルを小さくする」「クラス数を増やす」「共通化率を上げる」こと自体を成果としない。

## 2. 責務境界

分割候補は次の観点で判断する。

- 変更理由が異なるか
- 入出力と依存先を独立して説明できるか
- 単独で試験する価値があるか
- 障害時に独立して切り分けたいか
- 他責務の詳細を知らずに利用できるか

行数だけでは分割しない。短い処理でも変更理由が異なれば分離し、大きな処理でも一つの責務として不可分なら無理に細分化しない。

## 3. 禁止する分割

- 1処理を機械的に複数ファイルへ移しただけで依存関係が変わらない分割
- 実装を転送するだけの無意味な中継クラス
- 将来使うかもしれないという理由だけのインターフェース
- 具体的な責務名を持たない `Manager`、`Helper`、`Util` 等への集約
- 循環依存を生む共通化
- Platform固有事情を共通層へ漏らす共通化

これらの名称が常に禁止という意味ではない。責務を具体的に説明できない状態で逃げ先として使用することを禁止する。

## 4. 依存方向

原則として外部技術詳細から業務・Runtime契約を分離する。

概念上の方向は次を基準とする。

```text
HTTP / UI / Platform Entry Point
        ↓
Application orchestration
        ↓
Runtime / Domain contract
        ↓
必要な抽象境界
        ↑
GitHub / File / Platform persistence 等の実装
```

現行構造との衝突がある場合は、理想形へ一度に寄せるのではなく、契約維持を優先して段階的に解消する。

## 5. 既存契約の維持

v3.0.0は原則として意味論を変更しない。

- APIの要求・応答
- Runtimeの解決規則
- Recoveryの状態遷移とエラー分類
- GitHub書込時の競合判定
- 永続化の意味
- Windows / Android間で共有する意味論
- 画面上の既存機能

変更が必要と判断した場合は、リファクタリングへ混在させず別課題として扱う。

## 6. 実装前確認

対象コードを変更する前に、呼出元・呼出先・試験・共有型・Platform差異を横断確認する。

既存ファイルに処理が存在することを、責務配置の根拠にしてはならない。
