# 試験および回帰確認方針

## 1. 目的

v3.0.0は構造変更の規模が大きいため、「Buildが通る」だけを完了条件にしない。

既存機能と契約の意味論が維持されていることを、自動試験と手動確認の両方で確認する。

## 2. 自動試験

既存の以下を維持する。

- Windows単体試験
- Android単体試験
- Windows / Android整合性試験
- Shared試験
- Frontend試験
- 各Build / 静的確認

責務分離により独立試験可能になった処理は、必要に応じて局所的な試験を追加する。

既存試験を削除して新構造に合わせることで通過させてはならない。契約が同じなら既存期待値を維持する。

## 3. 回帰重点領域

- Application起動
- Portal / Shell / Navigation
- 主要画面の表示・操作
- Responsive挙動
- API要求・応答
- Runtime構築
- Master参照解決
- Workout集約
- Recovery
- GitHub読込・書込
- 競合・失敗時の分類
- ローカル永続化
- Windows / Android間の意味論

## 4. 段階試験

巨大な一括変更後に初めて試験することを避ける。

責務単位または移行単位ごとに、変更前の契約を確認し、変更後に該当試験を実行する。

問題が発生した場合は、その段階で停止して原因を解消してから次へ進む。

## 5. 手動試験

最終的な手動試験項目は製造後の差分と自動試験範囲を確認して確定する。

自動試験で十分に固定されている内部境界を、理由なく全件手動で再試験しない。一方、Shell、Navigation、Responsive、端末実動作等の視覚・統合領域は手動確認を重視する。

## 6. 合格条件

- 既存自動試験が通過する
- 新規に必要となった責務単位試験が通過する
- Windows / Androidの契約整合性が維持される
- 主要画面の機能回帰がない
- 既知の警告と新規異常を区別して記録できる
