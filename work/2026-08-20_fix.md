# Atlament Next — Basic Design / FIX

## Status

本資料は、Atlamentの将来方向性について現時点でFIXした基本設計・設計原則を整理する。
詳細実装方式は別途DB・実装設計で決定する。

---

## 1. Private GitHub Repository Data Integration

- AtlamentのデータSource of TruthはPrivate GitHub Repositoryとする。
- RepositoryをPublic化することは前提としない。
- Native Host ApplicationがGitHub APIを利用して必要なJSONデータを取得する。
- GitHub IntegrationはRead Onlyとし、RepositoryへのWriteは禁止する。
- FrontendへGitHub Tokenを公開しない。
- Local Dataは表示・Offline利用のためのLocal Copyとして扱う。
- Git cloneは原則行わず、Repository内でディレクトリ管理されている対象JSON群を取得する。
- Git metadata、commit SHA、history等はLocal Dataとして保持しない。

---

## 2. Zero-Cost Operation

Atlamentの継続運用費用は原則 `¥0` とする。

外部有料Server、RDBMS等を前提としたArchitectureは採用しない。

理由: 金がない。

---

## 3. Native Host Architecture

Primary PlatformはWindowsとし、C# Native Host Applicationを基底Architectureとする。

将来的なOptional Platformとして以下を想定する。

- Android / Kotlin
- iOS / Swift

新規Platform追加時にも既存FrontendへPlatform固有処理を追加しない。

### Architecture Principle

> FrontendはHost Platformを知らない。

Platform差異はNative Host側で吸収する。

---

## 4. Frontend Communication

Native HostとFrontendのCommunicationはlocalhost上のHTTP Request / Responseを基底とする。

Native BridgeをFrontend共通Interfaceとして採用しない。

Frontend側で以下のようなPlatform分岐を実装しない。

```text
Windows -> C# Bridge
Android -> Kotlin Bridge
iOS     -> Swift Bridge
```

各Native Hostが同一のlocalhost HTTP API Contractへ適合する。

---

## 5. Frontend Hosting

Native Host Applicationは原則としてFrontend AssetsまでHostingする。

```text
Native Host
├─ localhost HTTP Server
├─ Portal
├─ Dashboard
├─ Workout History
├─ Performance Detail
├─ Analytics
└─ Data / API
```

Frontendは可能な限りRelative URLでHost APIへアクセスする。

---

## 6. Host Storage Separation

Application Systemの管理情報は論理的に以下へ分離する。

```text
Application System
├─ Credential Storage
│  └─ GitHub Token
├─ Application Settings
│  ├─ Repository
│  ├─ Branch
│  ├─ JSON Path
│  └─ Token Metadata etc.
└─ Local Data Storage
   └─ JSON Data Directory
```

GitHub TokenはApplication System側で安全に保持し、Frontendへ提供しない。

---

## 7. Application Wake Up / Setup

Application wake up時、Application管理領域に必要なLocal Dataが存在するか確認する。

Local Dataが存在しない場合はSetup Guidanceを起動する。

Setup Guidanceの詳細内容は未FIXとし、今後調整する。

Local DataについてはGit Repository cloneを前提とせず、JSON Data Directoryを管理する。

---

## 8. Token Management / Expiration Notification

- GitHub TokenはNative Host Application System側で保存する。
- Token登録日時または更新日時をMetadataとして保持する。
- Token期限判定に必要な情報をApplication System側で管理する。
- Token有効期限10日前からPortalへ警告情報を表示する。
- 必要な情報取得・確認にはGitHub APIを利用可能とする。
- TokenそのものはFrontendへ提供しない。

具体的な期限算出方法・GitHub APIとの整合方法は詳細設計で決定する。

---

## 9. Data Synchronization

Application wake up時は毎回GitHubから対象JSON Data Directoryの取得を試行する。

- 手動Refreshを許可する。
- 更新有無に関係なく、正常取得したデータでLocal Dataを置換する。
- GitHub取得失敗時は既存Local Dataを継続利用する。
- 同期処理中はSystem側のLoading状態をFrontendへ通知可能とする。
- Frontendは取得処理完了後、取得結果をHost APIから取得してRenderingする。
- 取得失敗時はHost API経由でAlert情報をFrontendへ提供し、既存Local DataでRenderingを継続する。
- RepositoryへのWriteは禁止する。

---

## 10. Data Replacement / Rollback Principle

取得処理のExceptionによって、最後に正常利用できていたLocal Dataを破壊しない。

既存Local Dataが存在する場合、取得前に既存DirectoryをRenameしBackupとして保持する。

### Success

```text
Current -> BackupへRename
       ↓
New Data取得
       ↓
正常終了
       ↓
Backupを物理削除
```

### Failure

```text
Current -> BackupへRename
       ↓
New Data取得
       ↓
Exception
       ↓
取得したCurrent Dataを削除
       ↓
Backupを元の名称へRename Revert
```

不完全な取得データによって既存正常データを上書きしないことを基本原則とする。

---

## 11. Local Data Deletion

Application SystemからLocal Dataを削除可能とする。

削除実行後はApplication Processを終了し、localhost HTTP Serverも終了する。

```text
Delete Local Data
       ↓
Managed Local Data削除
       ↓
localhost Shutdown
       ↓
Application Process Kill
```

次回wake up時はLocal Data不存在としてSetup Guidanceへ遷移する。

---

## 12. Single Instance

Applicationの多重起動は禁止する。

Wake up時に同一Application Processが既に存在する場合、起動しようとした側でErrorを表示する。

ユーザーがOK等で確認後、新規Process自身を終了する。
既存Processには干渉しない。

---

## 13. Localhost Port

固定Primary / Secondary Port方式とする。

- Primary: `14108`
- Secondary: `45194`

```text
14108 available?
├─ YES -> Start
└─ NO
   ↓
45194 available?
├─ YES -> Start
└─ NO
   ↓
Error
   ↓
Application Kill
```

動的Port探索は基本方式としない。

---

## 14. Database Policy

現時点ではSQLite / RDBMS等のDatabase Layerを導入しない。

Private GitHub Repository上のJSONをSource of Truthとする。
Databaseが必要となる明確な要件が発生するまでArchitectureへ組み込まない。

---

## 15. Version / Distribution

外部配布は現時点で予定しない。

HostとFrontendは同一Version / 同一Application Unitとして管理する。
外部配布を前提としたCompatibility LayerやMigration機構は現時点では設計対象外とする。

---

## 16. Logging

Production用途の永続Logging基盤は設けない。

開発時にDebug Loggingを利用可能とするが、Token等のCredential / SecretをLogへ出力してはならない。

---

# Frontend / Visual Design Principles

## 17. UI Package Policy

各Frontend Frameworkで利用可能なUI Component / Visualization Packageは原則利用可能とする。

ApexCharts等のVisualization Packageを含め、外部UI Package自体を制約しない。

ただしApplication全域をUI Packageへ依存させない。

局所利用を原則とし、例として以下を想定する。

- Table
- Chip
- Tooltip
- Select / Date Picker
- Dialog
- Icon
- Chart / Visualization
- その他、小規模UI Component

Application全域のLayout、Typography、Color、Spacing、Navigation等は共通CSSによるAtlament Visual Identityを優先する。

Package採用は「利用可能だから使用する」ではなく、開発者がVisual / UX上の価値を認めた場合に行う。

---

## 18. Modern / Material Design

AtlamentのUIはModern Design / Material Designの設計思想を基本とする。

ただし特定のMaterial Design実装、UI Library、Architecture Sourceへの準拠は要求しない。
利用するFrameworkおよび開発者の判断へ委ねる。

実装手段よりも完成物としてのVisual Hierarchy、Surface、Elevation、Spacing、Interaction等の一貫性を重視する。

---

## 19. Color / Visual Feedback Policy

VisualizationおよびVisual Feedbackに使用する色の意味と基本ToneをAtlament全体で統一する。

| Role | Color Tone | Purpose |
| --- | --- | --- |
| Primary | 紫 / 青系 | Brand、主要UI、Visualization、Accent |
| Selected / Active | 緑系 | 選択中、Active、Focus対象 |
| Error / Critical | 赤系 | Error、処理失敗、異常状態 |
| Warning / Caution | 橙 / 黄系 | Warning、注意喚起 |

Semantic Colorは単なる装飾目的で乱用しない。

同一の意味には同一系統の色を使用し、Framework / UI Package / Visualization Package固有のDefault ColorよりAtlament Color Policyを優先する。

具体的なHEX値の完全統一は要求せず、Atlament全体の統一感を損なわない範囲で濃淡・明度・彩度を調整可能とする。

---

## 20. Motion Design Policy

CSS Animation / Transitionは採用可能とする。

ただし全項目への一律Animationは不許可とする。

Animationは装飾ではなく、状態変化・操作結果・画面遷移を伝達するVisual Feedbackとして扱う。

### Allowed Examples

- Hover時のElevation / Transform / Opacity
- Button / Chip等の状態変化
- 選択状態切替
- Accordion等の展開・収納
- Tooltip等の表示
- Chart描画Animation
- Pagination Animation
- その他、意味のある局所Animation

### Not Allowed

- 全Card / 全要素への一律Animation
- 常時動き続ける不要な装飾
- 情報取得・閲覧を妨げるAnimation
- 意味のない過剰演出

---

# Easter Egg / Experimental Feature

## 21. Easter Egg Architecture

Portalを軸としてEaster Egg機能を投入可能とする。

Easter Eggの状態管理、発火判定、進行制御等は原則として共通JavaScriptへ集約する。

各Frameworkは可能な限り描画 / Visual Feedbackのみを担当し、同一制御ロジックをFrameworkごとに重複実装しない。

```text
Shared JS
├─ Trigger
├─ State
├─ Progress Control
└─ Common Logic
       ↓
Framework
└─ Rendering / Visual Feedback
```

詳細構想は以下を参照する。

```text
work/ossan/おっさん.md
```

ただし、同資料のEaster Egg詳細仕様は現時点ではFIXしていない。
本資料でFIXするのは、Portalを軸とすること、および制御を原則Shared JSへ集約するArchitecture Principleまでとする。
