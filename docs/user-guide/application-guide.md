# Atlament 画面・機能ガイド

この資料は Atlament を利用する人向けに、各画面で「何ができるか」「何を表示しているか」を説明する。

内部実装の状態名やFramework名を覚える必要はない。

## ホーム

Atlamentを開いたときの入口。

### できること

- 各機能画面を開く。
- データ同期中、注意事項、エラー等の現在状態を確認する。

### 補足

一部のトレーニングデータに問題があっても、正常なデータを利用できる場合はAtlament全体が利用不能になるとは限らない。画面に注意事項が表示された場合は、必要に応じてデータ修復画面から対象を確認する。

---

## ダッシュボード

最近のトレーニング状況をまとめて確認する画面。

### 主な表示

- 今月のトレーニング回数
- 今月のセット数
- 今月のVolume
- 前月との件数・数値比較
- 最新のトレーニング
- 最近のトレーニング
- Volumeやセット数の推移
- 部位別の実施状況

### 数値の読み方

「今月」は現在の暦月を意味し、直近30日間ではない。

Atlamentは記録された回数・重量・セット数等を集計するが、明示的な評価機能がない限り「成長している」「刺激が足りない」等の判断は行わない。

---

## トレーニング履歴

過去のトレーニングを一覧・日付単位で確認する画面。

### できること

- トレーニング履歴を一覧表示する。
- カレンダーから日付を選ぶ。
- マシン、部位、ジム、期間等で履歴を絞り込む。
- トレーニング内容、セット、RIR、メモ等を確認する。
- マシンのパフォーマンス詳細へ移動する。

### 同じ日に複数回トレーニングした場合

Atlamentでは「日付」と「1回のトレーニング」を別のものとして扱う。同じ日に複数のトレーニング記録を持つことができる。

現在の日付画面は同日の記録をまとめて表示できる。将来の編集機能では、同日に複数記録がある場合に対象を勝手に決めず、編集する記録を選択できるようにする。

---

## マシン別パフォーマンス

特定のマシンについて、過去の実施履歴や推移を確認する画面。

### できること

- 表示するマシンを選択する。
- マシンごとのトレーニング履歴を確認する。
- 重量やVolume等の推移を確認する。

### マシンが指定されていない場合

別のマシンへ自動的に移動せず、表示するマシンの選択を求める。

存在しないマシンが指定された場合も、別のマシンへ勝手に置き換えず「指定されたマシンが見つかりません」と案内する。

### 比較について

重量やVolumeをパフォーマンス指標として比較する場合、原則として同じジム・同じマシンで比較する。異なるマシンの重量を単純に比べて能力の増減とは判断しない。

---

## 分析

一定期間のトレーニング記録を集計して確認する画面。

### 主な表示

- トレーニング回数
- セット数
- Weight / Volume
- トレーニング間隔
- 実施推移
- 部位別実施状況
- 週間頻度
- 使用マシン数・利用頻度
- ジム別の実施回数

### 期間

7日、28日、今月、3か月、6か月、全期間等から対象期間を選択する。

「今月」は現在の暦月を意味する。

### 分析結果について

この画面は記録された事実を集計する。明示的な評価モデルがない状態で、筋肥大効果、成長、停滞、刺激不足等を自動判定しない。

---

## アプリケーション設定

Atlamentがデータを取得するGitHub Repositoryや接続情報等を設定する画面。

### できること

- GitHub Repositoryの接続設定を確認・変更する。
- 認証情報を設定する。
- Workout / Machine Master / Gym Master の取得先を設定する。
- 同期を実行する。
- Application Frameworkの状態を確認する。

### データ種別ごとの規則

WorkoutやMaster Dataが「存在しなければならないか」「0件を許可するか」といったAtlament固有の規則を、利用者が任意のチェックボックスで変更する設計にはしない。

---

## リソース管理

GymやMachine等の基準情報を管理する画面。

### できること

- Gym情報を追加・編集する。
- Machine情報を追加・編集する。
- 既存情報をコピーして新規作成する。
- 使用しなくなった情報を論理削除する。
- 論理削除した情報を復元する。
- Main Gymを設定・変更する。
- Workoutから参照されている不明なGym/Machine IDを確認する。

### 削除について

過去のWorkout記録との関係を保持するため、通常操作ではMaster情報をGitHubから物理的に消さず「削除済み」として保持する。

---

## データ修復

壊れて安全に利用できなくなったデータを、内容を確認しながら修復する画面。

### 対象

「修復が必要なデータ」と判定されたResourceが対象になる。

内部状態名を理解する必要はない。画面では、何が問題なのか、どの項目を確認する必要があるのかを利用者向けに表示する。

### 基本的な流れ

1. 修復が必要なデータを選ぶ。
2. 元データから安全に回収できた値を確認する。
3. 未確定項目を入力・確認する。
4. 「修復内容を確認」でResource全体を検証する。
5. 問題がなければ「修復を確定」する。
6. GitHubへ保存後、Atlamentが同期・再検査して利用可能なデータへ反映する。

### 下書き

修復途中の内容は端末内に「下書き」として保存される。GitHub上のWorkout/Master Dataとして確定されるわけではない。

元データが別端末等で更新された場合、古い下書きをそのまま確定せず「元データが更新されています」と案内する。

### 元データ

必要に応じて修復対象の「元データ」を読み取り専用で確認できる。

これは汎用JSON editorではなく、直接Raw Dataを書き換える機能ではない。

### 保存に失敗した場合

GitHubへの保存が失敗した場合は失敗として表示し、保存できたように見せない。

GitHubへの保存自体は成功したものの、その後のAtlamentへの再反映に失敗した場合は「保存済み・反映失敗」と区別して案内する。この場合、GitHubへ保存済みの内容を自動的に巻き戻さない。

---

## エラー画面

要求された画面が存在しない場合、内部エラーが発生した場合、サービスを利用できない場合に表示する専用画面。

### 種類

- 404: 指定されたページが見つからない。
- 500: 内部処理でエラーが発生した。
- 503: 現在サービスを利用できない。

エラー画面は、通常画面の機能に依存して一緒に壊れないよう、独立した簡素な構成になっている。

---

## 画面に表示される状態の考え方

利用者向け画面では、内部実装の状態名より「何が起きていて、何ができるか」を優先して表示する。

例:

| 状況 | 利用者向け表現例 |
|---|---|
| 修復しないと安全に利用できない | 修復が必要なデータ |
| 利用できるが警告がある | 利用できますが確認事項があります |
| 修復中に元データが更新された | 元データが更新されています |
| GitHub保存成功、再反映失敗 | 保存済み・反映失敗 |
| 修復作業中の端末内データ | 下書き |

`Broken`、`Degraded`、`LKG`等は設計・実装内部では必要な用語だが、利用者がその内部用語を知らないと操作できないUIにはしない。
